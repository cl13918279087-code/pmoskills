## 2. 关键路径法（CPM）

### 2.1 概念定义

**关键路径**：项目中耗时最长的活动序列，决定项目最短完成时间。任何关键路径上的活动延迟都将导致整个项目延期。

### 2.2 银行业务关键路径识别

```
关键路径识别流程：
1. 列出所有活动及持续时间
2. 绘制网络图（节点法或箭头法）
3. 计算各路径总工期
4. 识别最长路径即为关键路径
5. 标记关键路径上的活动
```

**银行业务常见关键活动类型**：
| 活动类型 | 示例 | 典型工期 | 备注 |
|---------|------|---------|------|
| 监管审批 | 银保监报批、人民银行备案 | 30-90天 | 不可压缩 |
| 核心开发 | 账务核心重构、交易引擎改造 | 60-120天 | 可适度并行 |
| 联机切换 | 旧系统到新系统数据迁移 | 2-4小时 | 必须连续作业 |
| UAT测试 | 业务验收测试 | 15-30天 | 可压缩但有风险 |
| 合规审计 | 安全评估、渗透测试 | 10-20天 | 必须通过 |

### 2.3 关键路径输出格式

```markdown
## 关键路径分析结果

### 关键路径（总工期：XXX天）
| 序号 | 活动名称 | 活动编码 | 工期(天) | 开始时间 | 结束时间 |
|-----|---------|---------|---------|---------|---------|
| 1 | [活动1] | WBS-01 | X | YYYY-MM-DD | YYYY-MM-DD |
| 2 | [活动2] | WBS-02 | X | YYYY-MM-DD | YYYY-MM-DD |
| ... | ... | ... | ... | ... | ... |

### 关键路径总工期
- 最短项目工期：XXX天
- 关键路径占比：XX%
```

## 3. 依赖识别

### 3.1 依赖类型定义

| 依赖类型 | 代码 | 含义 | 银行业务示例 |
|---------|------|------|------------|
| 结束-开始（FS） | FS | 紧前活动结束后才能开始紧后活动 | 系统开发完成后才能UAT |
| 开始-开始（SS） | SS | 紧前活动开始后紧后活动才能开始 | 需求分析开始后即可启动环境准备 |
| 结束-结束（FF） | FF | 紧前活动结束后紧后活动才能结束 | 数据迁移结束后才能进行数据校验 |
| 开始-结束（SF） | SF | 紧前活动开始后紧后活动才能结束 | 灾备演练开始后生产监控才能停止 |

### 3.2 银行业务依赖关系矩阵

```markdown
## 依赖关系矩阵

### 活动依赖列表
| 紧前活动 | 紧后活动 | 依赖类型 | 延迟量(天) | 说明 |
|---------|---------|---------|-----------|------|
| 需求分析 | 方案设计 | FS | 0 | 需求冻结后开始设计 |
| 方案设计 | 核心开发 | FS | 0 | 设计评审通过后开发 |
| 环境搭建 | 单元测试 | SS | -5 | 环境就绪即可开始测试 |
| 核心开发 | 联调测试 | FS | 0 | 开发完成并通过自测 |
| 联调测试 | UAT | FS | 2 | 联调问题修复后2天 |
| UAT | 安全评估 | FS | 0 | UAT通过后开始 |
| 安全评估 | 投产准备 | FS | 0 | 安全问题修复后 |
| 投产准备 | 灰度发布 | FS | 0 | 准备工作完成 |
| 灰度发布 | 全量发布 | FS | 0 | 灰度验证通过 |
```

### 3.3 依赖识别流程

```
依赖识别五步法：
1. 梳理活动清单 - 确认WBS各工作包
2. 分析业务逻辑 - 根据银行业务流程确定先后顺序
3. 识别资源约束 - 同一团队同一时间只能做一件事
4. 识别外部依赖 - 监管审批、供应商、第三方系统
5. 确定时间延迟 - 活动间是否需要缓冲时间
```

### 3.4 依赖类型标注规则

- **强制性依赖**：银行业务法规、监管要求、合同义务
- **选择性依赖**：最佳实践、历史经验、可调整
- **外部依赖**：监管机构、第三方厂商、外汇管制政策

## 4. 工期估算

### 4.1 估算方法选择

| 方法 | 适用场景 | 精度 | 银行业务示例 |
|------|---------|------|------------|
| 类比估算法 | 历史数据丰富的同类项目 | ±30% | 信贷系统改造参考信贷工厂项目 |
| 参数估算法 | 有成熟模型的项目 | ±20% | 基于功能点估算开发工期 |
| 三点估算法 | 存在不确定性的项目 | ±15% | 新技术引入的系统建设 |
| 自下而上估算法 | 复杂项目、WBS完整 | ±10% | 核心系统重构 |

### 4.2 三点估算公式

```
乐观时间（O）：理想条件下最短工期
最可能时间（M）：正常条件下的预期工期
悲观时间（P）：最不利条件下的最长工期

期望工期 = (O + 4M + P) / 6
标准差 = (P - O) / 6
```

### 6.1 进度排序入口检查

```
输入检查清单：
□ WBS分解完成（至少3层结构）
□ 活动清单完整（无遗漏、无冗余）
□ 工期估算完成（已附估算依据）
□ 依赖关系初步识别
□ 约束条件明确（资源、监管、窗口期）
□ 假设条件记录
```

### 6.2 网络图绘制

```
步骤1：活动编号
- 按WBS编码体系统一编号
- 例：P03-D01-001 表示第三阶段开发工作第1个工作包第1个任务

步骤2：绘制网络图
- 推荐使用节点法（PDM）
- 确保无循环依赖
- 标注虚活动表示逻辑关系

步骤3：关键路径计算
- 前推法计算最早开始/结束时间
- 后推法计算最晚开始/结束时间
- 计算总浮动时间 = LS - ES
- 浮动时间为0的活动在关键路径上
```

### 6.3 计划编制

```
步骤4：确定计划日期
- 根据项目目标日期反推
- 或根据计算出的最短工期确定目标可行性

步骤5：资源平衡
- 检查关键路径资源冲突
- 如有冲突，考虑：
  * 资源调配（从非关键路径借调）
  * 加班（增加成本）
  * 快速跟进（增加风险）
  * 延后活动（非关键路径可延后）

步骤6：三层计划输出
- L1：里程碑清单 + 里程碑网络图
- L2：阶段计划 + 阶段资源需求
- L3：详细任务清单 + 每日/每周执行计划
```

### 6.4 计划评审与发布

```
步骤7：计划评审
- 技术评审：设计方案可行性
- 业务评审：业务流程匹配度
- 管理评审：资源可用性、监管合规性

步骤8：计划基线确认
- 建立进度基线（Baseline）
- 记录当前计划作为比较基准
- 确定偏差阈值（通常±10%）

步骤9：计划发布
- 向所有干系人发布计划
- 明确沟通机制和报告要求
- 建立变更控制流程
```

## 7. 进度风险识别

### 7.1 银行业务常见进度风险

```markdown
## 进度风险清单

| 风险ID | 风险描述 | 影响活动 | 影响工期(天) | 概率 | 风险等级 | 应对措施 |
|-------|---------|---------|------------|------|---------|---------|
| SR-01 | 监管政策变化 | 全项目 | 30 | 中 | 高 | 密切跟踪政策动向，提前沟通 |

| SR-03 | 第三方接口延期 | 联调测试 | 15 | 中 | 中 | 早期锁定接口规格，建立惩罚条款 |

```

### 7.2 进度风险应对策略

```
进度风险应对原则：
1. 规避 - 调整计划绕开风险
2. 转移 - 外包、保险、合同条款
3. 缓解 - 降低发生概率或影响
4. 接受 - 建立应急储备
```

## 8. 进度偏差监控

### 8.1 挣值分析（EVM）整合

```
进度绩效指标（SPI）：
SPI = EV / PV

- SPI > 1：进度超前
- SPI = 1：进度符合
- SPI < 1：进度滞后

进度偏差应对：
- SPI < 0.95：启动进度恢复计划
- SPI < 0.90：升级管理层干预
```

## 12. 最佳实践

1. **尽早识别依赖**：在WBS分解阶段即开始识别依赖关系
2. **关键路径可视化**：将关键路径图表张贴于项目室，持续提醒团队
3. **设置缓冲时间**：关键路径活动预留10%应急储备
4. **定期更新计划**：每周更新L3计划，每月审视L1/L2计划
5. **重视非关键路径**：非关键路径的严重延迟也会变成关键路径
6. **沟通计划变更**：任何计划调整需及时通知所有干系人
7. **记录实际工期**：为后续项目积累估算数据
