project-oversight

## Purpose

Establish and operate systematic project oversight that monitors progress against plan, identifies and analyzes deviations, manages escalations, and coordinates corrective actions — ensuring project leadership maintains situational awareness and can intervene early when issues emerge.

**This skill is essential for complex, multi-team projects** where centralized visibility is required to maintain control and coordination across functional groups and work streams.

## When to use
## Trigger this skill when

- A project requires systematic progress tracking beyond ad-hoc status updates
- Deviations from plan have occurred or may occur
- Escalation processes need to be formally managed
- Executive stakeholders require visibility into project health
- Corrective actions need to be tracked to closure
- Multiple work streams need coordination oversight

## Expected Inputs

### Required Inputs

| Input | Description | Example |
|-------|-------------|---------|
| project plan/baseline | Approved project plan with WBS, schedule, budget | "主计划含120个任务，18个里程碑" |
| current progress data | Actual progress against plan | "本周完成5个任务，2个任务延期" |
| deviation thresholds | Acceptable variance limits | "进度偏差>5%需报告，>10%需升级" |
| escalation criteria | When and how issues should be escalated | "组内无法解决的问题24小时内升级" |

| Input | Description |
|-------|-------------|
| previous oversight records | Historical deviation and escalation data |
| risk register | Current risks that may affect progress |
| change log | Recent changes affecting the plan |
| resource availability | Team capacity and allocation data |

### Health Score Calculation

| 维度 | 权重 | 评分标准 | 计算方法 |
|------|------|----------|----------|
| **进度健康** | 30% | 绿色(90-100), 黄色(70-89), 红色(<70) | (完成% / 计划%) × 100, 封顶100 |
| **成本健康** | 25% | 绿色(<100%), 黄色(100-110%), 红色(>110%) | (实际成本 / 计划成本) × 100 |
| **范围健康** | 20% | 绿色(无蔓延), 黄色(受控变更), 红色(失控变更) | 基于变更数量和影响 |
| **质量健康** | 15% | 绿色(缺陷率低), 黄色(缺陷率中等), 红色(缺陷率高) | 缺陷密度 vs 目标 |
| **风险健康** | 10% | 绿色(无RED), 黄色(1-2个RED), 红色(>2个RED) | 红区风险数量 |

**综合健康度计算：**
```
综合健康度 = 进度健康×30% + 成本健康×25% + 范围健康×20% + 质量健康×15% + 风险健康×10%

评级标准：
- 🟢 绿色(85-100): 项目正常推进
- 🟡 黄色(70-84): 需要关注，建议干预
- 🔴 红色(50-69): 高风险，需要积极干预
- ⚫ 黑色(<50): 项目危急，考虑终止或重构
```

## Deviation Analysis Framework

### Deviation Detection

| 监控维度 | 检测指标 | 预警阈值 | 行动阈值 |
|----------|----------|----------|----------|
| 进度 | SPI (进度绩效指数) | <0.95 | <0.90 |
| 进度 | 里程碑延期 | >3天 | >7天 |
| 成本 | CPI (成本绩效指数) | <0.95 | <0.90 |
| 成本 | 预算超支 | >5% | >10% |
| 范围 | 变更数量(周) | >3项 | >5项 |
| 范围 | 变更影响(工作量) | >5% | >10% |
| 质量 | 缺陷逃逸率 | >15% | >25% |
| 质量 | 测试覆盖率 | <80% | <70% |

```markdown
# 偏差分析报告
**项目：** [项目名称]
**报告期：** [日期范围]
**分析人：** [姓名]
**日期：** [日期]

## 1. 偏差概览

| 维度 | 计划值 | 实际值 | 偏差量 | 偏差率 | 状态 |
|------|--------|--------|--------|--------|------|
| 完成百分比 | 50% | 45% | -5% | -10% | 🔴 |
| 预算(万元) | 600 | 620 | +20 | +3.3% | 🟡 |
| 里程碑#3 | 2024-03-01 | 2024-03-05 | +4天 | — | 🟡 |

## 2. 根因分析 (5-Why)

**问题描述：** 进度落后5%

```
Why 1: 为什么进度落后？
→ 原因：开发任务比预期多

Why 2: 为什么开发任务比预期多？
→ 原因：需求变更导致返工

Why 3: 为什么需求变更导致返工？
→ 原因：需求确认延迟

Why 4: 为什么需求确认延迟？
→ 原因：业务方评审时间不足

Why 5: 为什么业务方评审时间不足？
→ 原因：评审会议安排在UAT前2周
```

**根本原因：** 需求确认流程与开发计划衔接不当，导致变更影响被放大

## 3. 影响评估

| 影响项 | 影响程度 | 说明 |
|--------|----------|------|
| 项目结束日期 | 延期5-7天 | 可能影响上线计划 |
| 项目预算 | 增加3-5% | 额外人力投入 |
| 范围质量 | 风险上升 |赶工可能影响质量 |
| 团队士气 | 中等影响 | 赶工压力增加 |

## 4. 纠正措施

| 措施 | 预期效果 | 责任人 | 完成日期 | 资源需求 |
|------|----------|--------|----------|----------|
| 1. 冻结需求范围 | 防止进一步蔓延 | 总体组 | 立即 | 无 |
| 2. 增加开发资源 | 缩短工期 | PMO | 3日内 | 2人月 |
| 3. 优化测试策略 | 压缩测试周期 | 测试组 | 5日内 | 评估中 |

## 5. 预测与建议

**基于当前趋势的预测：**
- 项目结束日期：可能延期5-7天
- 最终预算：可能超支3-5%

**建议：**
1. 接受轻微延期，聚焦质量
2. 或批准增加资源以压缩工期

## 6. 后续跟踪

| 检查点 | 日期 | 负责人 | 验证方式 |
|--------|------|--------|----------|
| 措施1验证 | 2024-03-15 | [姓名] | 需求变更记录 |
| 进度复核 | 2024-03-22 | [姓名] | SPI计算 |
```

## Escalation Management

### Escalation Trigger Criteria

| 级别 | 触发条件 | 示例 |
|------|----------|------|
| **L1 - 关注** | 单维度预警阈值触发 | SPI<0.95 |
| **L2 - 警告** | 多维度预警阈值触发 | SPI<0.95 且 CPI<0.95 |
| **L3 - 升级** | 行动阈值触发或组内无法解决 | SPI<0.90 或 里程碑延期>7天 |
| **L4 - 危急** | 综合健康度<70或需委员会决策 | 多项严重偏差 |

## Corrective Action Management

### Corrective Action Process

```
发现问题 → 偏差分析 → 制定措施 → 审批措施 → 实施措施 → 跟踪验证 → 闭环
    ↓
┌────────────────────────────────────────────────────────────┐
│ Step 1: 问题识别                                            │
│   - 日常监控发现偏差                                         │
│   - 团队报告问题                                             │
│   - 风险事件触发                                             │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 2: 偏差分析                                            │
│   - 量化偏差（量/率/趋势）                                    │
│   - 根因分析（5-Why）                                        │
│   - 影响评估（进度/成本/范围/质量）                           │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 3: 制定纠正措施                                        │
│   - 列出可能的纠正方案                                       │
│   - 评估每个方案的影响和可行性                                 │
│   - 选择推荐方案                                             │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 4: 审批纠正措施                                        │
│   - L1/L2: PMO经理批准                                      │
│   - L3: 项目总监批准                                         │
│   - L4: 委员会批准                                           │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 5: 实施与跟踪                                          │
│   - 分配责任人和完成日期                                     │
│   - 纳入日常监控                                             │
│   - 设置验证检查点                                           │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 6: 闭环验证                                            │
│   - 验证措施效果                                             │
│   - 确认偏差已纠正或接受                                     │
│   - 记录经验教训                                             │

```

| # | 检查项 | 验证标准 |

| 1 | 及时性 | 监控报告在约定时间前完成 |

| 4 | 可追溯性 | 偏差有根因分析，措施有责任人 |
| 5 | 行动导向 | 每项偏差有明确的纠正措施 |
| 6 | 升级合规性 | 按定义的阈值触发升级 |
| 7 | 闭环验证 | 纠正措施有验证记录 |

## Common Failure Modes

| 失败模式 | 说明 | 应对 |
|----------|------|------|
| ❌ 监控滞后 | 问题发生很久后才被发现 | 建立自动化预警机制 |
| ❌ 偏差归因不当 | 把问题归咎于外部而非根因 | 强制根因分析（5-Why） |
| ❌ 纠正措施无效 | 采取措施后问题依然存在 | 跟踪验证，未改善则升级 |
| ❌ 升级不及时 | 问题恶化后才上报 | 明确升级阈值和时限 |
| ❌ 数据不一致 | 不同报告数字矛盾 | 建立单一数据源 |
| ❌ 忽视早期预警 | 对🟡信号视而不见 | 🟡必须分析并记录原因 |
| ❌ 纠正措施执行不力 | 只计划不执行 | 纳入周会跟踪，PMO监督 |

## Procedure

> **EN Alias**: 本章节同时标记为 `## Operating Procedure (6-Step Process)`，内容完全一致。

## Operating Procedure (6-Step Process)

```
Step 1: 数据收集与汇总
  ├─ 从各功能组收集周进展数据
  ├─ 更新任务管理系统和进度报告
  ├─ 汇总风险、问题、变更状态
  └─ 准备原始数据供分析

Step 2: 偏差检测与分析
  ├─ 计算PV/EV/AC和SPI/CPI
  ├─ 对比实际vs计划在各维度
  ├─ 识别超出阈值的偏差
  └─ 对🟡及以上偏差进行根因分析

Step 3: 健康度评估
  ├─ 按五维度计算健康分
  ├─ 综合计算健康度评分
  ├─ 确定项目健康等级
  └─ 识别需关注区域

Step 4: 升级管理
  ├─ 检查升级触发条件
  ├─ 对达到L3/L4的问题编制升级简报
  ├─ 提交升级简报给相应层级
  └─ 跟踪升级处理进度

Step 5: 纠正措施跟踪
  ├─ 验证已批准措施的执行进度
  ├─ 对未按期完成的措施进行督促
  ├─ 评估措施有效性
  └─ 对无效措施提出替代方案

Step 6: 报告与沟通
  ├─ 更新监控仪表盘
  ├─ 生成周报/月报
  ├─ 分发相关干系人
  └─ 记录会议决议和跟踪项
```
