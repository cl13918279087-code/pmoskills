cross-dept-coordination

## Purpose

Establish effective coordination mechanisms for projects that span multiple departments or organizational units — ensuring alignment on dependencies, efficient resource sharing, timely conflict resolution, and shared accountability for cross-functional outcomes.

**This skill is critical for enterprise-wide initiatives** (e.g., ERP implementations, digital transformations, process reengineering) where success depends on coordinated execution across organizational boundaries.

## When to use
## When to use this skill

- A project involves multiple departments beyond the primary sponsoring unit
- Dependencies exist between departments that could create bottlenecks
- Resource conflicts or priority disputes have occurred or are likely
- Joint decisions require consensus among department representatives
- A project governance structure needs cross-functional representation
- Inter-department communication has broken down in previous projects

## Dependency Management

### Dependency Types

| 类型 | 说明 | 示例 | 管理重点 |
|------|------|------|----------|
| **硬依赖** | 必须按顺序完成，无替代方案 | 上游需求未完成，下游无法开工 | 提前识别，确保上游优先 |
| **软依赖** | 有一定灵活性，可以并行或替代 | UI设计可并行于后端开发 | 尽量并行，优化路径 |
| **资源依赖** | 需共享特定资源 | 共享测试环境、共享专家 | 预约机制、时间协调 |
| **信息依赖** | 需接收特定信息/数据 | 需获得上游输出作为输入 | 明确时间窗口 |
| **审批依赖** | 需获得特定审批/签字 | 需业务部门验收签字 | 提前触发、跟踪 |

## Conflict Resolution Protocol

### Conflict Types and Resolution Paths

| 冲突类型 | 特征 | 首选解决方式 |升级路径 |
|----------|------|--------------|---------|
| **资源冲突** | 争抢人员/设备/预算 | 资源协调会议 | PMO→项目总监→委员会 |
| **优先级冲突** | 任务优先顺序争议 | 优先级排序会议 | PMO→项目总监 |
| **技术方案冲突** | 技术路线意见不一致 | 技术评审会 | 架构组→技术委员会 |
| **范围冲突** | 范围界定或变更争议 | 变更评审会 | 总体组→PMO→委员会 |
| **进度冲突** | 时间节点无法达成共识 | 进度协调会 | PMO→项目总监 |
| **质量冲突** | 质量标准意见不一致 | 质量标准评审 | 质量组→PMO |
| **沟通冲突** | 信息不对称或误解 | 直面会议 | 接口人→PMO |

### Conflict Resolution Process (5-Step)

```
冲突发生 → 评估级别 → 首次解决 → 升级（如需要） → 闭环记录
    ↓
┌────────────────────────────────────────────────────────────┐
│ Step 1: 冲突识别                                            │
│   • 当事人或观察者识别冲突                                   │
│   • 记录冲突基本信息（双方、时间、内容）                        │
│   • 初步判断冲突类型                                         │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 2: 评估级别                                            │
│   L1: 组内可解决（双方直接协商）                              │
│   L2: 跨组需协调（接口人+PMO协调）                            │
│   L3: 需项目总监裁决                                         │
│   L4: 需委员会决策                                           │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│ Step 3: 首次解决尝试                                        │
│   • L1: 当事人在48小时内直接协商                              │

│   • L3/L4: 准备材料提交裁决                                  │

                            ↓

│ Step 4: 升级处理（如首次解决失败）                            │

                            ↓
```

### Conflict Resolution Meeting Structure

```markdown
# 冲突解决会议议程
**会议主题：** [冲突简述]
**会议时间：** [日期时间]
**参与方：** [部门A代表] vs [部门B代表]
**主持人：** [PMO/项目总监]

---

## 议程

1. 冲突背景陈述（各10分钟）
   - 部门A陈述立场和诉求
   - 部门B陈述立场和诉求

2. 共同点识别（10分钟）
   - 识别双方已达成共识的点
   - 明确核心分歧点

3. 方案探讨（20分钟）
   - 探索可能的解决方案
   - 评估各方案利弊

4. 决议（10分钟）
   - 确定最终解决方案
   - 明确执行责任和时间
   - 记录后续跟踪项

## 会前准备

- [ ] 冲突双方分别准备立场陈述（不超过1页）
- [ ] 收集相关支持数据或证据
- [ ] 确定各自的底线和可接受范围
- [ ] 指定本部门的决策代表（能当场做决定的人）
```

| **问题解决会** | 按需 | 冲突方+PMO | 30-60分钟 | PMO | 冲突解决、决策 |
| **部门负责人协调会** | 每月 | 部门负责人/高管 | 90分钟 | 项目总监 | 战略协调、资源决策、升级处理 |

### Meeting Effectiveness Guidelines

| 原则 | 说明 |
|------|------|
| **有明确的议程** | 每次会议有预设议程，会前分发 |
| **有明确的产出** | 每项议题有决议或后续行动 |
| **有明确的跟踪** | 行动项指定责任人和完成日期 |
| **避免重复** | 已有其他渠道覆盖的内容不在会上讨论 |
| **尊重时间** | 准时开始和结束，控制发言时间 |
| **决策人在场** | 确保能做决定的人参加会议 |

## Escalation Matrix

### Escalation Levels and Criteria

| 级别 | 触发条件 | 升级到 | 时间要求 | 升级形式 |
|------|----------|--------|----------|----------|
| **L1** | 日常协调问题 | 部门接口人 | 即时 | 即时沟通 |
| **L2** | 接口人无法解决的协调问题 | 部门PM代表 | 24小时 | 书面+会议 |
| **L3** | PM代表无法解决的管理问题 | PMO/项目总监 | 48小时 | 升级简报 |
| **L4** | 资源/优先级等重大决策 | 项目管理委员会 | 按会议安排 | 正式上会 |

### Escalation Response Timeline

```
升级接收 → 确认受理 → 初步响应 → 解决方案 → 执行确认
    ↓
• 升级接收后4小时内确认受理
• 24小时内提供初步响应
• 48小时内提交解决方案
• 解决后确认执行效果
```

### Information Sharing Rules

| 规则 | 说明 |
|------|------|
| **透明度** | 及时共享影响其他部门的信息 |
| **准确性** | 共享信息需核实，避免误导 |
| **完整性** | 关键信息不选择性披露 |
| **保密性** | 敏感信息按规定渠道传递 |
| **可追溯** | 重要沟通有书面记录 |

## Quality Gates

| # | 检查项 | 验证标准 |
|---|--------|----------|
| 1 | 覆盖完整性 | 所有参与部门都纳入协调框架 |
| 2 | 依赖清晰度 | 所有跨部门依赖有明确的责任人和时间 |
| 3 | 协议有效性 | 资源共享协议各方签字确认 |
| 4 | 升级路径明确 | 每种冲突类型有明确的升级路径 |
| 5 | 会议效率 | 会议有议程、产出和跟踪 |
| 6 | 决策可行性 | 跨部门决议可执行、有跟踪 |
| 7 | 问题解决率 | L2及以下冲突在承诺时间内解决≥80% |

## Common Failure Modes

| 失败模式 | 说明 | 应对 |
|----------|------|------|
| ❌ 依赖遗漏 | 跨部门依赖未识别就开工 | 强制依赖识别流程，纳入WBS检查 |
| ❌ 承诺失信 | 部门承诺的资源/时间无法兑现 | 承诺需部门负责人签字，定期跟踪 |
| ❌ 责任推诿 | 问题在部门间踢皮球 | 明确RACI，有争议时PMO临时指定 |
| ❌ 会议低效 | 大量会议但无实质产出 | 严格会议管理，无议程不开会 |
| ❌ 升级延误 | 问题恶化才升级，错过最佳干预时机 | 明确升级阈值，到阈值强制升级 |
| ❌ 沟通断层 | 部门内传递失真或信息丢失 | 建立书面沟通渠道，定期同步 |
| ❌ 文化冲突 | 不同部门工作风格差异导致摩擦 | 提前建立沟通规范，尊重差异 |

## Procedure

The cross-department coordination follows a 6-step lifecycle:

```
Step 1: 干系人映射与框架设计
  ├─ 识别所有参与部门及其在项目中的角色
  ├─ 分析部门间依赖关系类型
  ├─ 评估潜在冲突领域
  └─ 设计协调层级和机制

Step 2: 协议与机制建立
  ├─ 制定资源共享协议
  ├─ 确定联合会议机制
  ├─ 建立冲突解决协议
  └─ 设计升级矩阵

Step 3: 依赖管理实施
  ├─ 识别并登记所有跨部门依赖
  ├─ 与各部门确认依赖承诺
  ├─ 建立依赖跟踪机制
  └─ 监控依赖交付状态

Step 4: 日常协调运作
  ├─ 按会议机制召开跨部门会议
  ├─ 协调日常执行问题
  ├─ 更新依赖状态
  └─ 协调资源分配

Step 5: 问题与冲突处理
  ├─ 接收并评估冲突
  ├─ 组织冲突解决会议
  ├─ 执行升级流程（如需要）
  └─ 跟踪决议执行

Step 6: 持续改进
  ├─ 收集协调机制执行反馈
  ├─ 识别流程改进点
  ├─ 更新协调框架
  └─ 记录经验教训
```
