## 目的

## Purpose

对需求文档进行完整性、正确性、一致性和可执行性评审；检查范围变更情况；评估变更请求对项目进度、成本、质量的影响；输出评估报告与控制建议，确保需求受控、范围清晰、变更合规。

## 触发时机

## When to use

- 需求文档编写完成后，进入评审阶段
- 范围变更发生时，需要评估变更影响
- 需求歧义或冲突导致执行困难
- 项目进度偏差，需要分析需求层面原因
- 关键里程碑前，需要复核需求稳定性
- 需求变更频繁（变更率超过阈值）
- 项目进入UAT/投产阶段，需确认需求实现完整性

| 输入项 | 描述 | 示例 |
|--------|------|------|

| scope statement | 范围说明书（已批准的项目范围基线） | 项目范围说明书、In-Scope/Out-of-Scope清单 |

## 评审维度框架

### 1. 完整性评审（Completeness Review）

| 评审项 | 评审内容 | 检查标准 |
|--------|----------|----------|
| 业务需求覆盖 | 所有业务场景是否都有对应的需求描述 | 业务流程图→需求功能点映射，无遗漏 |
| 功能需求完整性 | 每个业务功能是否都有明确的功能描述 | 功能清单完整性检查 |
| 非功能需求完整性 | 性能、安全、可用性、可维护性需求是否明确 | 非功能需求清单及量化指标 |
| 接口需求完整性 | 系统间接口需求是否完整定义 | 接口清单、接口协议、接口约束 |
| 数据需求完整性 | 数据需求（数据来源、格式、量级、生命周期）是否完整 | 数据需求说明书、数据字典 |
| 边界条件完整性 | 异常场景、边界条件是否都有描述 | 异常流程清单、边界条件测试用例 |

### 2. 正确性评审（Correctness Review）

| 评审项 | 评审内容 | 检查标准 |
|--------|----------|----------|
| 需求描述准确性 | 需求描述是否准确反映业务意图 | 业务方确认签字 |
| 需求可验证性 | 需求是否可测试、可验证 | 有明确的验收标准/测试通过条件 |
| 需求无歧义性 | 需求描述是否清晰、无歧义 | 需求评审无歧义问题记录 |
| 需求一致性 | 同一需求在不同文档中描述是否一致 | 跨文档一致性检查 |
| 需求可行性 | 需求在现有技术条件下是否可实现 | 技术可行性评估报告 |
| 需求依赖清晰度 | 需求间依赖关系是否明确 | 需求依赖矩阵 |

### 3. 变更影响评估（Change Impact Assessment）

| 影响维度 | 评估内容 | 分析方法 |
|----------|----------|----------|
| 范围影响 | 变更是否影响项目范围边界 | 范围影响分析（增量/减量/修改） |
| 进度影响 | 变更对项目进度的影响（天/月） | 进度影响估算（资源法/类比法） |
| 成本影响 | 变更对项目成本的影响 | 成本影响估算（工时×单价） |
| 质量影响 | 变更对交付质量的影响 | 质量风险分析 |
| 资源影响 | 变更对资源的需求变化 | 资源需求分析 |
| 风险影响 | 变更带来的新风险或风险变化 | 风险影响评估 |

## Procedure

### Step 1: 需求收集与梳理

```
1.1 收集需求文档
    ├─ 收集BRD、PRD、需求规格说明书等文档
    ├─ 收集需求变更记录和变更申请
    ├─ 收集项目范围说明书（基线版本）
    └─ 收集需求跟踪矩阵（如有）

1.2 建立需求基线
    ├─ 梳理已批准的需求范围（基线需求）
    ├─ 识别新增需求（未批准变更）
    ├─ 识别需求变更（已批准和待批准）
    └─ 建立需求版本快照

1.3 需求分类
    ├─ 按业务领域分类（核心业务/支持业务/管理业务）
    ├─ 按优先级分类（P0/P1/P2/P3）
    ├─ 按变更类型分类（新增/修改/删除/澄清）
    └─ 按风险等级分类（高/中/低）
```

### Step 2: 完整性评审

```
2.1 业务需求覆盖度检查
    ├─ 对照业务流程图，逐项检查需求覆盖
    ├─ 识别缺失的业务场景和功能点
    └─ 输出需求缺失清单

2.2 功能需求完整性检查
    ├─ 检查每个功能的需求描述完整性
    ├─ 验证功能描述的清晰度和可理解性
    └─ 输出功能需求检查表

2.3 非功能需求检查
    ├─ 检查性能需求（响应时间、吞吐量、并发数）
    ├─ 检查安全需求（认证、授权、审计、加密）
    ├─ 检查可用性需求（可用性指标、容错要求）
    └─ 输出非功能需求检查表

2.4 接口需求检查
    ├─ 检查系统间接口定义完整性
    ├─ 验证接口协议和数据格式定义
    └─ 输出接口需求检查表

2.5 输出完整性评审结论
    ├─ 汇总完整性检查结果
    ├─ 识别关键缺失项和高风险项
    └─ 提出完善建议
```

### Step 3: 变更影响评估

```
3.1 变更识别与分类
    ├─ 识别范围内的变更请求
    ├─ 按影响程度分类（重大变更/一般变更/微小变更）
    └─ 确定需要评估的变更范围

3.2 范围影响分析
    ├─ 分析变更对In-Scope/Out-of-Scope的影响
    ├─ 评估是否需要调整范围边界
    └─ 识别范围蔓延风险

3.3 进度影响估算
    ├─ 评估变更所需工作量（人天）
    ├─ 评估对关键路径的影响
    ├─ 估算进度延迟风险
    └─ 计算对里程碑的影响

3.4 成本影响估算
    ├─ 计算直接成本影响（人力/材料/第三方）
    ├─ 计算间接成本影响（管理成本/机会成本）
    ├─ 评估预算超支风险
    └─ 计算对项目ROI的影响

3.5 质量影响评估
    ├─ 评估变更对系统稳定性的影响
    ├─ 评估对已测试功能的影响（回归风险）
    ├─ 评估对整体质量目标的影响
    └─ 提出质量保障建议

3.6 输出变更影响分析报告
    ├─ 汇总各维度影响评估结果
    ├─ 按影响程度排序变更项
    ├─ 提出变更处理建议（批准/拒绝/分批/暂缓）
    └─ 明确变更审批责任人
```

### Step 4: 控制建议输出

```
4.1 范围控制建议
    ├─ 制定范围变更控制流程
    ├─ 明确范围变更审批层级
    ├─ 建立范围冻结机制
    └─ 制定范围蔓延防范措施

4.2 需求变更控制建议
    ├─ 建立需求变更评估标准
    ├─ 制定变更优先级评估规则
    ├─ 建立变更评审机制（CCB）
    └─ 明确变更沟通和通知机制

4.3 进度控制建议
    ├─ 建立进度偏差预警机制
    ├─ 制定进度压缩措施（赶工/快速跟进）
    ├─ 建立进度变更审批流程
    └─ 制定进度恢复计划

4.4 成本控制建议
    ├─ 建立成本监控机制
    ├─ 制定成本超支预警阈值
    ├─ 建立预算变更审批流程
    └─ 制定成本优化措施

4.5 输出控制建议书
    ├─ 汇总各项控制建议
    ├─ 明确责任人执行计划
    └─ 确定跟踪检查机制
```

### Step 5: 评审归档与跟踪

```
5.1 评审材料归档
    ├─ 归档评审报告和检查清单
    ├─ 更新需求基线版本
    ├─ 更新需求跟踪矩阵
    └─ 维护变更日志

5.2 跟踪整改进度
    ├─ 跟踪缺失需求的补充情况
    ├─ 跟踪改进建议的执行情况
    └─ 确认整改完成并验证效果

5.3 经验沉淀
    ├─ 总结需求控制方法论改进点
    ├─ 更新需求评审检查表模板
    └─ 沉淀典型案例到知识库
```

## 失败模式规避

| 失败模式 | 描述 | 应对措施 |
|----------|------|----------|
| 需求遗漏导致返工 | 关键业务场景未识别到需求中，导致开发后补充 | 建立需求覆盖度检查机制；业务方签字确认 |
| 变更影响评估不足 | 变更影响评估不充分，导致进度/成本超支 | 建立标准化的变更影响评估模板；引入CCB评审 |
| 范围蔓延失控 | 需求变更累积导致范围大幅膨胀，项目失控 | 建立范围变更控制流程；设定变更阈值预警 |
| 需求歧义导致返工 | 需求描述歧义导致开发/测试理解不一致 | 需求评审加入歧义检查；建立需求澄清机制 |
| 变更频繁影响稳定性 | 需求变更过于频繁，影响开发节奏和系统稳定性 | 建立变更评审机制；设定变更窗口期 |
| 质量目标偏离 | 变更累积影响项目质量目标 | 建立质量影响评估机制；设置质量底线 |

## 需求评审检查清单

### 完整性检查

- [ ] 业务流程全覆盖（主流程+分支流程+异常流程）
- [ ] 功能需求完整（增删改查+业务规则+校验逻辑）
- [ ] 非功能需求明确（性能/安全/可用性/可维护性）
- [ ] 接口需求完整（系统间+模块间）
- [ ] 数据需求完整（数据格式+数据量级+数据生命周期）
- [ ] 边界条件完整（正常+异常+极限情况）

### 正确性检查

- [ ] 需求描述准确反映业务意图
- [ ] 每个需求都有明确的验收标准
- [ ] 需求描述无歧义（可向不同人解释为相同含义）
- [ ] 跨文档需求描述一致
- [ ] 需求在技术上可实现
- [ ] 需求间依赖关系明确

### 变更影响评估检查

- [ ] 每个变更都有范围影响分析
- [ ] 每个变更都有进度影响估算（人天）
- [ ] 每个变更都有成本影响估算
- [ ] 每个变更都有质量风险分析
- [ ] 重大变更已通过CCB评审
- [ ] 变更处理建议明确（批准/拒绝/分批/暂缓）

## 变更影响评估矩阵

| 变更类型 | 范围影响 | 进度影响 | 成本影响 | 质量影响 | 风险等级 |
|----------|----------|----------|----------|----------|----------|
| 需求新增（重大） | +15%以上 | +2周以上 | +10%以上 | 高风险 | 🔴 高 |
| 需求新增（一般） | +5-15% | +3天-2周 | +3-10% | 中风险 | 🟡 中 |
| 需求新增（微小） | <5% | <3天 | <3% | 低风险 | 🟢 低 |
| 需求修改（重大） | 影响核心功能 | +2周以上 | +10%以上 | 高风险 | 🔴 高 |
| 需求修改（一般） | 影响辅助功能 | +3天-2周 | +3-10% | 中风险 | 🟡 中 |
| 需求删除 | 可能影响关联功能 | 视情况 | 可能节省成本 | 低风险 | 🟢 低 |
